Peer review for a long-horizon hobby engine · Zig 0.16.0 · ~14.5k LOC in src/ · 140 commits · sole author: John Hatch

1. Executive summary

Yes — your intended split makes complete sense. This is not a vibe-coded toy that happens to compile. It is a real graphics/engine learning platform with a clear center of gravity: pure-Zig math, a glTF-native animation pipeline, and an experimental game shell in examples/bullets where architecture is still being discovered.

The codebase reads as two interleaved voices: short imperative commits that move pieces around (“refactored shapes”, “added view caching”) and longer design-shaped commits with bullet bodies (“Add ResourceManager with factory methods…”). That maps well to your claim — you own the interesting core, AI has been used more heavily for migration, glTF, plans, and mechanical refactors.

Bottom line The engine’s technical soul is sound: column-major math, Transform/Movement as orientation primitives, Cook-Torrance PBR path, cubic-spline animation, and a growing scene/resource pattern in bullets. The main risks are not “wrong architecture” but layer blur, doc/status drift, a few concrete API bugs, and the gravitational pull of AI toward filling core with game-adjacent systems.

5. Core deep dive

Rendering spine

Path is classic modern OpenGL: load mesh attributes into VAOs, bind materials in MeshPrimitive.draw, drive joints via jointMatrices[100], apply per-node nodeTransform. constants.zig is a smart habit — CPU/GPU contract in one place — even though sync is still manual.

Recent RenderContext work (plan 014) is architecturally mature: one camera-derived value per frame (projection, projection_view, view, view_pos, time) instead of every object setting matrices. That is the kind of incremental engine hygiene that scales without over-designing a full render graph.

Animation — the crown jewel and the risk

animator.zig is the densest intellectual property in the project. It carries:

  • glTF skin / joint hierarchy with inverse bind matrices
  • Linear and cubic-spline (Hermite) channels for T/R/S
  • WeightedAnimation multi-clip blending with quaternion care
  • Preprocessed per-node animation data unions for type-safe dispatch

The ASSIMP → glTF migration philosophy documented in the changelog — rewrite internals, preserve call sites where useful — is a senior move. You kept games working while replacing the substrate.

animation_fsm.zig (comptime-generic over a state enum) is elegant Zig. Used well by ToonSoldier in bullets. It sits on the core/game fence: reusable, but game-policy flavored.

Asset loading

GltfAsset is the right abstraction boundary: parse/load/configure once, then buildModel(). Normal generation modes (skip / simple / accurate) and custom texture assignment are practical bridges for imperfect author-pipeline assets. Dual storage note (buffer.data vs buffer_data) is the kind of scar tissue worth keeping documented — you already fixed a real bug from that confusion.

6. Math library

~2k lines of pure Zig: Vec2/3/4, Mat3/4, Quat, ray helpers, easing. Column-major, OpenGL-compatible. CGLM is still vendored but commented out of the build — the “Complete CGLM elimination” commits (2025-06) were a milestone.

Why this matters for a 30-year systems person Writing your own math forces you to confront conventions (row vs column, -Z forward, handedness, matrix×vector order) that engines usually hide. Your fromDirection docs, Transform basis tests, and the -Z forward fix commit show that confrontation actually happened and left tests behind. Keep that habit.

Naming is mostly consistent (toNormalized, methods on types). Occasional typos survive (fromRotaion in Transform) — harmless but a reminder that AI and humans both leave lint.

7. examples/bullets — the real product right now

This is where the project’s future game shape is being negotiated. It is more interesting as architecture than as a game.

Patterns in play

  • Scene vtable (scene.zig): type-erased update/draw/deinit with optional method detection via std.meta.hasMethod. Comment even asks “Could we use a union with pointers?” — good design journal left in code.
  • SceneObject vtable: draw / updateLights / getTransform. Lightweight entity interface without ECS.
  • World + scene arena: switching scenes deinit GL, tear down arena, rebuild. Correct instinct for lifetime isolation.
  • ResourceManager factory: create → auto-track → deleteAll. Plan 015 reasoning is solid (MonoGame ContentManager analogue).
  • Motion debugging: MotionType / MotionObject in debug scene — treat the scene as a control surface for core Movement/Camera behavior.
  • Projectiles: instanced cubes, spread, gravity field ready (gravity: f32 = 0.0), turret — pure experiment sandboxes.

Alternate design nearby

examples/scene_tree explores union-based nodes vs interface nodes. Having both bullets’ vtables and scene_tree’s unions is healthy research — just don’t promote both into core prematurely.

Read of current focus bullets is doing what a good hobby engine lab should: prove that core APIs compose into a game loop, without freezing the game architecture too early. PageUp/PageDown scene switching is a nice touch for A/B of scene designs.

11. What is genuinely good

  1. End-to-end glTF ownership. Parse → asset → mesh/GPU → skinning → draw. No black-box importer runtime for the main path.
  2. Math you can trust (and test). Eliminating CGLM and keeping Transform orthonormality tests is serious engineering practice.
  3. Debuggability culture. glTF report tool, F12 screenshot + uniform JSON, motion object selectors, axis lines, scene switching. Systems people debug systems — this codebase reflects that.
  4. Layered plans. Numbered plans 001–015 with backlog clustering is better than most hobby projects. The “horizontal layers, always demonstrable” philosophy is sound.
  5. Zig 0.16 currency. Tracking language breakage (ArrayList API, Io, process.Init) is itself a learning track.
  6. bullets as architecture sandbox separate from “ship a game” pressure. Correct hobby structure.

12. Interesting discoveries

12.1 Core is heavier on “engine services” than pure graphics

Exported from core/root.zig: Camera, Movement, Input, ResourceManager, AnimationStateMachine, SoundEngine, Random… These are reasonable, but they expand core beyond “graphics and model support.” bullets already treats ResourceManager as the scene’s factory; Input is window/engine glue. Worth deciding which are engine platform vs graphics core — maybe later a src/engine/ or keep flat but mentally tiered.

12.2 Two polymorphism experiments coexist

bullets: runtime vtables with *anyopaque. scene_tree: tagged unions / interface experiments. Neither is wrong. The interesting learning question is Zig-specific: when is comptime enough, when do you want type erasure for heterogeneous scene lists?

12.3 Shader global texture unit allocator

shader.zig uses module-level texture_unit_map / next_available_unit. Clever auto-bind, but process-global. Fine for single-window hobby apps; would bite multi-context or multi-thread later. Awareness > rewrite for now.

12.4 Legacy is still legible in the tree

  • ASSIMP comments in angrybot / animation_example
  • finalBonesMatrices uniform marked phased out
  • Dual lighting uniform naming (legacy vs standardized)
  • Empty stub examples/bullets/scene/spheres.zig
  • temp/ full of notes, old bullets, screenshots — a personal lab notebook

That is not failure; it is archaeology. For a hobby project it can stay. For learning clarity, occasionally pruning or labeling “historical” reduces cognitive load.

12.5 Docs volume vs code volume

~800 lines of CLAUDE.md + CHANGELOG + DEVELOPMENT, plus 15+ plan files. Much of the prose is high-ceremony status writing. Useful as session memory for AI; less useful as your personal map. Consider a short docs/review/ or NOTES.md that is unapologetically human and sparse.

12.6 Test coverage is concentrated where you learned the hardest

Unit tests cluster on Transform, Movement, Camera/Gimbal, retain/remove utils, some math. Integration test for GLB. Animator / asset_loader / mesh have far less automated coverage relative to complexity. That pattern matches “I wrote tests when orbit math betrayed me” — good instinct — and points to the next high-value test targets if you want them.

13. Friction & technical debt (prioritized)

High value to address when it blocks you

  • API drift across apps. angrybot still feels older; bullets is modern; level_01 mid-migration. Not urgent to unify, but when teaching yourself “the” way to load a model, pick bullets’ RM path as the reference.
  • Manual shader/constant sync. Documented honestly in constants.zig. A tiny codegen or test that greps shaders for required names would be a classic systems-person quality tool.
  • Plan status stale. Plans 004/005 still “planned” while FSM and multi-model scenes partially exist in code. Reconcile to avoid false sense of unfinished foundation.

Medium — polish when touching nearby code

  • Naming: occasional snake leftovers, typos (fromRotaion)
  • Commented-out dead methods in Model (playClip, transitions)
  • ResourceManager incomplete vs plan (no name maps, not all shape types)
  • libs still carries full assimp/cglm trees (~1GB under libs/) — fine if offline/vendored preference, heavy clone cost

Low — leave until curious

  • Shadow maps, IBL, post — backlog is appropriately aspirational
  • ECS / Bevy-style assets — correctly deferred in plan 015 analysis

16. Learning opportunities (matched to your background)

With compilers/debuggers/OS/cloud background, the highest-yield learning surfaces here are not “write another CRUD system” but:

  1. Numerical & geometric correctness — quaternions at poles, matrix decomposition, skinning math. You have already been living here.
  2. Data-oriented GPU feeding — instancing in bullet system, joint matrix packing, attribute layout contracts.
  3. Lifetime management as systems design — arenas per scene, GL object lifetime vs Zig memory, factory vs manual delete.
  4. Language evolution as ongoing curriculum — Zig 0.14→0.15→0.16 API churn is a feature for a lifelong learner.
  5. Spec engineering — glTF is a large external standard; using AI on the parser while you own the runtime model is a healthy hybrid.
  6. Architecture without product pressure — bullets can try vtables, unions, FSMs, until one feels like your style.

18. Recommendations (lightweight, non-prescriptive)

  1. Keep writing bullets by hand. It is the right place for structure discovery. Promote to core only after repeated use.
  2. Treat glTF + asset_loader as AI-eligible with your review gate. Matches your stated intent exactly.
  3. Fix loadGltfAsset when next in ResourceManager — small, real bug.
  4. Refresh active-plans / CLAUDE status so tools and humans share the same story: bullets + RenderContext + RM are current, not 2025-08 foundation narrative alone.
  5. Optional: one-page “engine map” you maintain yourself — ten lines of truth beats 300 lines of AI changelog.
  6. When stuck on math/animation, use AI as a rubber duck and second calculator, not as the author of the final algorithm.
  7. Do not rush shadows/IBL until you enjoy the current lab. Backlog is permission, not obligation.
Does this make sense? Yes. Using AI as an assistant on a personal learning engine is a coherent stance. The codebase already shows you can absorb AI-generated bulk without surrendering the interesting problems. The discipline is continuing to choose which problems are yours.
